# Evidence & Provenance

Every judge-facing number in this repository, with the artifact it comes from and
the command that regenerates it. If a figure is not in this document, it is not a
claim the project makes.

**This is a demonstration built on a synthetic dataset.** There is no connection
to any railway signalling, dispatch, or asset-management system, and no live data
feed. Dates, assets, trains, crews and corridors are generated.

---

## 1. Metric scopes — do not mix

Four distinct scopes exist. Each has its own artifact, and the UI labels which
one it is showing on every screen that displays figures.

| Scope | Artifact | Generated by | What it covers |
| :--- | :--- | :--- | :--- |
| **Baseline full run** | `benchmarks/full_run_metrics.json` | `python -m optimizer.main` | All 30,000 tasks over the 14-day horizon |
| **Demo scenario** | `optimization_metrics.json`, `optimized_block_plan.{json,csv}` | `python demo.py` | The 62-task subset the guided demo renders |
| **Decision trace** | `decision_trace.json` | `python scripts/generate_decision_trace.py` | Candidate-by-candidate evaluation for one task |
| **Replan scenario** | `replan_output/` (git-ignored) | `python demo_closed_loop.py` | One disrupted task re-solved |

Conflating the first two is what previously produced a "53 scheduled / 0.18%"
headline: a 62-task demo was being reported as if it had attempted all 30,000.

## 10. Train delay and holding

Delay is computed from physical data, not assumed:

    traversal_minutes = section_length_km / min(train_speed, line_speed) x 60
    detour_delay      = sum(bypass sections) - direct section

Both inputs come from `corridors_sections.csv` and `trains.csv`. Where a section
lacks length or speed the result is `null` and the UI says "not computable"
rather than printing a number.

`scripts/generate_ritvik_scenarios.py` writes four scenarios to
`frontend/src/data/ritvik_scenarios.json`, each a real engine run. The Live
Operations screen and the Event Simulator render these; nothing is hand-written.

| Scenario | Event | Priority | Result |
| :--- | :--- | :--- | :--- |
| `reroute` | EVT-001, SEC-0007 has headroom | class 2 | `TRN-SIM-001` REROUTED via SEC-0004 → SEC-0007 → SEC-0008 → SEC-0010, **+16 min** (computed from section length / speed) |
| `hold` | EVT-006, all bypasses saturated | class 2 | `TRN-SIM-006` HELD **35 min** until the block is handed back (wait ≤ 45-min limit) |
| `replan` | EVT-002, all bypasses saturated | class 1 | 4 bypasses rejected, 0 feasible; priority-1 train is never held → `REPLAN_REQUEST` |
| `block_unavailable` | EVT-003, the block itself is closed | — | route search skipped entirely → `REPLAN_REQUEST` |

**HOLD** is a real alternative action: when no bypass is feasible, a train may
wait for the possession to be handed back if the wait is within
`RitvikConfig.max_acceptable_hold_minutes` (default 45) **and** the train is not
`priority_class` 1. EVT-002 fails both tests (priority 1, 90-min wait), so its
documented `REPLAN_REQUEST` outcome is unchanged; EVT-006 is the demo's holdable
case.

**Safety buffer.** `RitvikConfig.safety_buffer_minutes` (default 0) widens the
possession window on both sides before the overlap test. It was defined but
never applied before this pass; it is now wired through `ConflictDetector`.

Sequencing and downstream (knock-on) impact are **not implemented** and are not
claimed — `trains.csv` records one section occupancy per train with no onward
itinerary.

`replan_request.json` now derives `rerouting_attempted` and
`alternative_route_available` from what actually ran, and carries the rejected
route candidates with the reason the search recorded. A `BLOCK_UNAVAILABLE`
closure short-circuits before any route search and now reports
`rerouting_attempted: false`.

Artifacts: `frontend/src/data/ritvik_scenarios.json`
(`scripts/generate_ritvik_scenarios.py`).

| Predicted risk | `risk_signal` (Neev score, 30-day probability, priority) |

| **Estimated delay** | 0 min for this possession — no service is displaced |

For `TASK-000005` the trace reports **0 conflicting and 0 adjacent** services:
the earliest train on SEC-0004 that day arrives at minute 338, well outside the
00:00–03:20 window plus the ±60 min C008 buffer. That is why the night slot
wins, and it is checkable against `trains.csv`.

Conflicting and adjacent are reported separately: a conflict blocks the
possession (C002, must be zero), an adjacent service only carries passenger-impact
weight (C008).

## 15. Dynamic allocation — criteria coverage

Rendered on the Live Operations screen and generated with the scenarios.

| Criterion | Status | Basis / limitation |
| :--- | :--- | :--- |
| delay | COMPUTED | section_length_km / min(train speed, line speed) |
| capacity | MODELLED | RitvikConfig.section_capacities — Capacities are configured constants, not a dataset column. |
| train priority | APPLIED | trains.csv priority_class; class 1 is never held |
| route availability | SEARCHED | route_topology.json adjacency + block closures — Prototype topology: 22 of 200 sections have adjacency data. Conflicts on sections outside it cannot be rerouted and escalate to replanning. |
| safety constraints | APPLIED | safety_buffer_minutes=0 widens the possession window before overlap testing |
| rerouting | IMPLEMENTED | BFS over all simple paths, four feasibility gates |
| holding | IMPLEMENTED | wait <= 45 min and priority_class != 1 |
| downstream impact | NOT_IMPLEMENTED | No knock-on delay propagation. trains.csv records one section occupancy per train with no onward itinerary, so downstream impact cannot be derived and is not scored. |
| sequencing | NOT_IMPLEMENTED | No precedence or platform-ordering model exists. |

**Topology.** Rerouting adjacency in `route_topology.json` covers 22 of 200
sections. Conflicts on sections outside it cannot be rerouted and escalate to
replanning. This is a prototype graph, not the modelled network.

**Capacity.** Section capacities are constants in `ritvik/config.py`, not a
dataset column, and the demos adjust them per scenario to force each branch.

**Downstream impact and sequencing are not implemented.** `trains.csv` records a
single section occupancy per train with no onward itinerary, so knock-on delay
cannot be derived; no score is invented for it.

## 16. Train projection for the planning timeline

`frontend/src/data/section_trains.json` — reproduce with:

```bash
PYTHONPATH=. python scripts/generate_section_trains.py
```

The Authority timeline draws maintenance possessions against the train movements
they have to fit around. That requires per-train timings, which the frontend
previously did not have: `section_traffic.json` carries only aggregate counts.
This artifact is a **projection of `trains.csv`, not a model**.

| Metric | Value |
| :--- | ---: |
| Source rows (`trains.csv`) | 12,000 |
| Rows within plan scope | 176 |
| Rows dropped for missing timing | 0 |
| Records emitted | 176 |
| Sections covered | 43 |

**Projection rule.** Restricted to the `(section_id, date)` pairs present in
`optimized_block_plan.json`, plus the sections referenced by the replanning
scenarios on every plan date (so a conflict scenario always has train context,
including the 2026-09-08 replanned window). Ordered by
`(section_id, date, arrival_minute, departure_minute, train_id)`.

**What is and is not done to the data.** `arrival_minute` and `departure_minute`
are copied verbatim from the source row. Nothing is sampled, smoothed, or
generated. A row missing either timing field is dropped rather than imputed, and
the dropped count is recorded in the artifact's own `provenance` block. Where a
selected section/date has no projected record, the timeline says so rather than
drawing a placeholder bar.

Corroboration: the earliest projected train on SEC-0004 for 2026-09-07 arrives at
minute 338, which matches the figure §12 derives independently from `trains.csv`
when explaining why the 00:00–03:20 night window carries zero adjacent services.

**Conflicts are never inferred from this artifact.** The timeline's conflict lane
is drawn only where an artifact already establishes a conflict
(`decision_trace.json → train_impact.conflicting`, or a replanning scenario's
`conflict.overlap_window`). Overlap arithmetic is not performed in the UI.

Asserted by `tests/test_section_trains.py`: source fidelity, verbatim timings,
scope correctness, deterministic ordering, byte-identical regeneration, and
internally consistent provenance counts.

## 17. Claims this project does not make

- No live or real-time railway data. All operational events are simulated and
  read from `ritvik_demo_events.json`.
- No REST API or backend service. The frontend reads committed JSON artifacts;
  it does not invoke the optimizer.
- No integration with Indian Railways or any operator system.
- No external notifications, audit-register writes, or persistence. Task status
  changes and verification actions live in React state for the session only.
- The frontend does not run the solver. The 868 s baseline run is precomputed;
  the "Re-optimize" control applies the replan the Python engine already produced.
- No train sequencing or precedence logic.
- No equipment or machine identifiers exist anywhere in the dataset, so no
  equipment allocation is claimed.
- Controller decisions (approve / modify / reject) and verification actions are
  session state only.
- Neev training is not reproducible here; only evaluation is.
